## Part 1 — Copy.ai prompts (help articles, macros, and email)

### 1. Ticket-to-article pipeline
```
Three customers submitted the same question this week. Here are their ticket threads:

TICKET 1: [PASTE FULL TICKET THREAD]
TICKET 2: [PASTE FULL TICKET THREAD]
TICKET 3: [PASTE FULL TICKET THREAD]

Write a help center article that answers all three phrasings. Structure:
- H1: The question phrased the way a customer would type it into Google (under 70 chars)
- One-paragraph answer (2-3 sentences) at the top for scanners
- Numbered step-by-step walkthrough
- "What to do if this didn't work" troubleshooting section with 2-3 branches
- Related articles (3 suggestions at the bottom)

Tone: clear, calm, no jargon. Assume the reader is not technical.
```

### 2. Help center article from release notes
```
We just shipped this feature. Here are the internal release notes:

[PASTE RELEASE NOTES]

Write a help center article that explains the new feature to existing users. Structure:
- H1: What the feature does, in plain English (under 70 chars)
- 2-sentence "what changed and why it matters" intro
- "How to use it" section with 3-5 numbered steps
- "Before you start" prerequisites box (permissions, plan requirements, integrations)
- 2 FAQ entries (anticipate the most common confusion points)
- One-paragraph "what's not changing" reassurance for users worried about disruption

Tone: informative, confident, no marketing language.
```

### 3. Ticket macro (reusable reply template)
```
Write a ticket macro (reusable reply template) for this common question:

QUESTION: [DESCRIBE THE COMMON QUESTION]

The macro should:
- Start with a 1-sentence direct answer (no "Thank you for reaching out" filler)
- Include 3-5 numbered steps if the answer involves actions
- End with a "If this didn't work" branch pointing to escalation or a related help article
- Be under 150 words (agents will paste and lightly edit this)
- Use bracketed placeholders for [CUSTOMER NAME], [PRODUCT NAME], and [LINK]

Provide 3 tone variants:
1. Friendly (for B2C consumer apps)
2. Professional (for B2B SaaS)
3. Empathetic (for billing, cancellation, or frustration-prone tickets)
```

### 4. Escalation summary (tier-1 to tier-2)
```
A tier-1 support agent needs to escalate this ticket to tier-2 / engineering. Here is the full ticket thread:

[PASTE TICKET THREAD]

Write an escalation summary that a tier-2 engineer can read in 30 seconds and start debugging. Structure:
- 1-sentence problem statement (what the customer is trying to do and what's blocking them)
- Customer environment: [PLAN], [BROWSER/DEVICE], [INTEGRATIONS if known]
- Reproduction steps (numbered, exact clicks)
- Expected behavior vs. actual behavior (1 sentence each)
- Error message or status code (if any)
- What tier-1 already tried (list the troubleshooting steps already attempted)
- Suggested investigation area (logs, API response, config, database) — best guess

Format: 5-8 sentences max. No customer-friendly tone — this is internal engineering communication.
```

### 14. Localization-ready article rewrite
```
Rewrite this help center article to be localization-friendly for translation into 5+ languages.

ARTICLE: [PASTE ARTICLE TEXT]

Apply these rules:
- Replace idioms ("once you've got that sorted," "jump into," "heads up") with literal phrasings
- Replace sports/cultural metaphors with universal descriptions
- Shorten sentences to under 20 words (translation engines handle short sentences better)
- Replace gerunds ("we'll be setting up your workspace") with imperative ("set up your workspace")
- Replace passive voice with active voice
- Replace contractions ("you'll," "we've") with full forms ("you will," "we have")
- Keep all product names, button labels, and UI element names as-is (these stay in English)

### 24. Video vs. article decision guide
```
A support team has limited video production capacity. Help them decide which help center topics should be articles, which should be videos, and which should be both.

Write a decision framework:

INPUT: List of 20 support topics (paste them here: [PASTE TOPICS])

For each topic, classify as:
- ARTICLE ONLY: The topic is a simple lookup or short answer. Text + screenshot is sufficient. Video adds no value.
- VIDEO ONLY: The topic requires seeing a multi-step UI flow in motion. Text alone confuses more than it helps.
- BOTH: The topic is complex enough to warrant both formats — article for scannable reference, video for first-time learners.
- INTERACTIVE: The topic is best served by an in-app guided tour, not a static article or video.

- If the answer is a single number or word → Article only
- If the flow has 5+ sequential UI steps → Video (or both)
- If the flow involves timing, animation, or "wait for X to load" → Video
- If the topic is troubleshooting with many branches → Article only (video can't branch)
- If the topic is onboarding/critical-path → Both

Output: a table with columns: Topic, Classification, Rationale, Estimated Production Time

### 28. Accessibility audit checklist
```
Create an accessibility audit checklist for a help center.

HELP CENTER URL: [URL]
NUMBER OF ARTICLES: [N]
CURRENT ACCESSIBILITY STATUS: [UNKNOWN / WCAG 2.1 AA PARTIAL / WCAG 2.1 AA COMPLIANT]

Checklist (30 items):
1. Every article has an audio version (Speechify or human-narrated)
2. Every image has alt text describing the screenshot content
3. Every video has closed captions (not auto-generated — human-reviewed)
4. Every video has a text transcript below it
5. Color contrast meets WCAG 2.1 AA (4.5:1 for normal text)
6. No information is conveyed by color alone (always paired with text or icon)
7. Keyboard navigation works through all articles and menus
8. Focus indicators are visible on all interactive elements
9. Heading hierarchy is logical (H1 → H2 → H3, no skipped levels)
10. Link text is descriptive (no "click here" — use "Read the billing guide")
11. Form fields in help center search have labels
12. Error messages are announced by screen readers (ARIA live regions)
13. Skip-to-content link is present
14. Language is declared in the HTML lang attribute
15. Content is readable at 200% zoom without horizontal scrolling
16. No content flashes more than 3 times per second
17. PDFs are tagged (not flat image scans)
18. Every table has a caption or summary
19. Every form has a submit button (not just Enter key)
20. Touch targets are at least 44x44px (for mobile help center)
21. No time limits on reading content
22. Auto-playing video/audio can be paused
23. Help center search has voice input option (for motor-impaired users)
24. Every article has a "last updated" date for content accuracy
25. Related articles are programmatically linked (not just visual)
26. Breadcrumbs are present and structured (for screen reader navigation)
27. Print stylesheet exists (some users print articles for offline reference)
28. No invisible focus traps
29. Content reading level is appropriate (aim for grade 8-10)
30. Privacy policy and support contact are accessible from every page

Score each item: PASS / FAIL / NOT APPLICABLE. Prioritize the FAILs by impact.
```
